# 分支改动判定

> 用途：判定本轮两项 git 改动是否合理，并登记核验记录与后续约束。
> 判定日期：2026-11-12｜证据图例见 `_shared/写作规范.md` 第二节（五档）。
> 说明：全文用「旧开发分支」代称，不写旧名全称；不引用 vps 分册的编号体系与 sha。

## 1. 判定 A：从 `main` 建立独立 `serverless` 文件系统

**结论：部分合适。**

| 分项 | 判定 |
|---|---|
| 意图 | 合理。本分册的主题（先判定要不要后端、纯单机 0 元、平台合规）与 vps 分册（整机成本、低价机体检）在计价口径、运用方式与操作步骤上都不同，隔离有价值 |
| 机制可行性 | 可行。工作区干净、无同名分支、无 CI 硬编码分支名、`main` 为纯祖先起点，`git switch -c serverless main` 一步可达 |
| 数据风险 | 低但有。`main` 只有 2 个旧基线文件且落后 66 提交；删继承文件后与 `main` 文件层脱钩；同名会话导出文件在 `vps` 仍被跟踪，日后合回会产生删除冲突 |
| 长期维护 | 主要代价：形成两套编号体系与两本台账，任一侧改数据需各自升版、各自回填，长期双轨维护 |
| 替代方案 | 从 `vps` 派生会继承 56 个不相关文件，违背隔离意图；空 orphan 分支会丢掉与 `main` 的祖先关系；单分支加子目录隔离不足 |

**成立条件（必须长期遵守）**：① 保持为独立主题分支；② 不做双向合并；③ 需要复用时走 `cherry-pick` 或复制单文件后改写；④ 不追求两系列最终统一。若长期意图是统一，则此项应判「不合适」。

## 2. 判定 B：旧开发分支改名为 `vps`

**结论：合适。**

| 分项 | 判定 |
|---|---|
| 意图 | 改进。更贴合仓库主题，去掉工具名绑定 |
| 机制可行性 | 已完成且设置正确：本地名、`[origin/vps]`、`branch.vps` 段、远端新名四项一致 |
| 数据风险 | 无数据丢失；代价是 6 处文档漂移（本次修正）与 1 处 stale 远端跟踪引用（本次 prune） |
| 长期维护 | 丢失原命名前缀的状态信号，靠进度看板与标签补偿；无 CI 配置，不影响流水线 |
| 替代方案 | 保留旧名（语义不贴合，不取）；新建分支后删旧分支（等价但多一步，已完成无需重做） |

**剩余收尾**：`git fetch --prune` 清理 stale 引用 + 6 处文档修正；历史 reflog 与两份会话导出中的旧名属于 Git 历史与历史快照，不可改写，不构成「不合适」。

## 3. 收尾动作记录

| # | 动作 | 分支 | 结果 |
|---|---|---|---|
| 1 | `git fetch --prune origin` | `vps` | stale 远端跟踪引用已清理 |
| 2 | 6 处旧名改为 `vps` + 历史计划补沿革说明 | `vps` | 全库旧名 0 命中 |

| 4 | `git switch -c serverless main` | 新建 | 基于 `945d142` |

## 4. 与目录清单的关系

本判定所依据的最终目录为 17 文件：2 个根配置 + 主报告 + 三份单开 + 2 份底座 + 2 份附录 + 免费层取样 + 判定 + 3 本台账。不建 `chapters/`、`labs/` 骨架，不建 vps 分册的成本模型文件。
